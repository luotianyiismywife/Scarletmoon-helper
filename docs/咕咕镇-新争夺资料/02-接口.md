## 1. 入口与认证

### 1.1 进入流程（GET 跳转链）
```
bbs.kfpromax.com/fyg_sjcdwj.php?go=play&xl=2   (xl=2 咕咕镇 / xl=1 咕咕线2)
    → www.momozhen.com/next.php                  (进入确认页, 按钮"进入咕咕镇")
    → www.momozhen.com/fyg_index.php             (游戏主页)
```

**自动登录链（2026-08-12 实测补全 + 2026-08-23 实测修正）⭐：**
```
bbs.kfpromax.com/fyg_sjcdwj.php?go=play&xl=2    (论坛域, 带 2ed4e_* cookie)
    → 302 Set-Cookie 下发新 fyg2019_gameuid/gamepw/endtime/logme（会话刷新占位）
    → www.momozhen.com/next.php                  (登录确认页, 按钮"进入咕咕镇")
    → www.momozhen.com/fyg_index.php             (带刷新后的新 cookie 才返回个人信息)
```
- **入口链的关键**：`fyg_sjcdwj.php` 的 302 响应会 **Set-Cookie 下发新的 fyg2019_***（服务器刷新会话）；随后 `fyg_index.php` **必须携带这批新 cookie** 才能登录成功，带旧 cookie 会被拒（返回 9 字符"请重新登录并刷新！"）
- **端到端成功标志**：`fyg_index.php` 返回含"个人信息"（约 8KB）；失败时返回 27 字节"请重新登录并刷新！"
- **UA 必须与浏览器一致**（2026-08-23 血泪）：PHPWind 论坛校验 UA 版本，旧版 UA（如 rv:137.0）请求论坛会被强制登出（重定向 login.php）→ 入口链全链路失败。浏览器实际发 `rv:156.0`（Nightly 版本号去 a1 后缀）。脚本 `tools/get_cookies.py` 已改为动态读 `application.ini` 版本生成 UA
- 游戏 cookie 的 `gameuid` = 论坛 uid（同源）；`m=li` 是自动链无需确认页（`next.php` 是手动路径）
- **论坛 cookie 过期 → 游戏也进不去**（跳转链校验失败）；`tools/get_cookies.py --login`（账号密码）或 `--refreshggz`（复用论坛 cookie）均可一键刷新

### 1.2 认证 Cookie（咕咕镇独立体系）
```
fyg2019_gameuid=<uid>             用户ID（=论坛 uid）
fyg2019_gamepw=<哈希>             "游戏密码"（哈希值，入口链每次刷新会变）
fyg2019_endtime=<时间戳>          时间戳（≈服务器刷新会话时的时间，**非未来过期点**，见下）
fyg2019_logme=1                登录标记
PHPSESSID=<会话ID>               游戏会话（**不落盘**，脚本需在会话内自动管理）
```

**⚠️ 单会话机制（最重要，2026-08-18/23 两次实测）⭐：**
- 咕咕镇**同一时刻只有一个会话生效**（单会话）。
  - 脚本刷新 cookie（`--login`/`--refreshggz`/入口链）→ 服务器建新会话 → **顶掉浏览器**会话（浏览器再开游戏页变"请重新登录"）
  - 浏览器打开游戏页/导航入口链 → 服务器发新会话 → **顶掉脚本**会话（脚本所有请求变"请重新登录" 9 字符 / f=1 变 27 字节"请重新登录并刷新！"）
  - 谁后刷新谁生效。日常脚本跑完后不要马上开浏览器游戏页；反之亦然
- **⚠️ cookie.txt 与会话不同步陷阱（2026-08-23 血泪）**：`cookie.txt` 里存的 `fyg2019_gamepw`/`PHPSESSID` 只是**某个时刻的快照**。若浏览器随后又导航入口链，服务器下发新 `gamepw` 顶掉 cookie.txt 的会话——cookie.txt 不会自动同步浏览器，于是脚本用**已失效的旧 cookie** 请求：`fyg_read.php` 全返回 27 字节"请重新登录并刷新！"（**而 `fyg_index.php` 可能仍正常返回页面**，两者校验不一致，极易误判为"限流"）。排查顺序：先查会话是否有效（用**浏览器当前会话**或重新 `--refreshggz`），再谈限流
- **`endtime` 语义（2026-08-23 实测）**：值≈服务器刷新会话时的时间（甚至比当前早几十秒），**不是**未来过期点。真正会话状态在**服务端 PHPSESSID session**；判断登录成功只能看端到端请求（`fyg_index.php` 是否含"个人信息"），不能只看 endtime 大小
- 旧资料"cookie 有效期约 1 天"应理解为**会话约 1 天自然过期**，需每日刷新；且**任何一侧重新登录都会使旧会话立即失效**
- 已登录判定：`fyg_index.php` 含"个人信息"（约 8KB）

### 1.2b safeid 令牌提取（slack 源码验证）
- **safeid 从 `fyg_index.php` 页面提取**：正则 `&safeid=([^"]+)"` 匹配第一个
- 每个用户/会话固定（实测页面内统一值 `<safeid>`）
- 所有 `fyg_click.php` / `fyg_v_intel.php` 动作必须携带

## 3. 核心接口

### 3.1 数据读取：`fyg_read.php`（POST）

Content-Type: application/x-www-form-urlencoded
Body: f=<区块ID> [&id=xx &ca=xx &zid=xx]

| f 值 | 内容 |

**f=20 详情弹窗结构（实测 2026-08-06）：**
- 左列 = 所选装备（属性+颜色），右列 = 当前同部位装备（对比）
- 操作按钮按 ca 不同：
  - `ca=3` 仓库：`穿上装备`(puton→c=3) / `丢弃装备`(stdel→c=7) / （若可熔炼）`熔炼该装备为护身符`(pirl→c=9+yz)
  - `ca=4` 沙滩：`放入仓库`(stpick→c=1)
  - `ca=2` 仓库护身符：`强化`(6万贝壳) / `放入我的饰品栏`(puto→c=22) / `销毁该护身符`(pirl→c=9)
  - `ca=1` 饰品栏护身符：`放入仓库 (将不会起效)`(puti→c=21)
- 熔炼资格：词条总值约 ≥410%（样本 406%不可熔 / 425%可熔）**且品质 ≥稀有**（2026-08-10 实测：品质数字 ≥3，418% 品质2不可熔，返回"至少需要稀有级别的装备才可以熔炼"），与词条颜色/神秘属性无关；**熔炼产物固定 = 星铜苹果护身符 随机属性+N**

**2026-08-06 实测补充：**
- `c=1` 拾取：**重复拾取**返回 `卡片不存在。`（实际装备已进仓库，属正常）；正确流程是 `f=20&id=<沙滩id>&ca=4` 打开详情弹窗 → 弹窗内"放入仓库"按钮 `stpick(id)`；沙滩 id 与 zbtip 的 id 一致
